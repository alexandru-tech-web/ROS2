# ViPRO schema reconciliation — TASK-002R

Date: 2026-09-23  
Schema reconciled: `experimental-manifest` version `1.0.0`  
Evidence baseline: TASK-001 ViPRO inventory at repository revision
`0d7d864ba85805090d97edcf639586ff27f457c8`

## Scope and decision

TASK-002R reconciles the experimental-data contract with the architecture
actually found by TASK-001. It does not alter runtime, control, logging, the
Modbus skeleton, TASK-001 artifacts, or the TASK-002 schema/tests.

Decision:

> The TASK-002 schema can represent all experimental-data concepts evidenced
> by TASK-001 without a schema change.

The populated example is
`research/configs/vipro_manifest_current.yaml`. It is deliberately a
`SIMULATION` / `PLANNED` structural manifest, not a physical run. This avoids
inventing an acquisition time, trial result, calibration, data artifact, or
ABB interface that the repository does not contain.

TASK-001 used the audit-specific provenance label `MANUAL_REFERENCE`. The
corresponding canonical TASK-002 value is `MANUAL`; no evidence was promoted
to `MEASURED` or `IDENTIFIED`. Values generated by or describing the present
simulator remain explicitly distinguishable from physical measurements.

The manifest contains no physical-current, drive-torque, external-torque or
temperature signal records. Their absence is intentional: TASK-001 found no
such acquisition path. Adding a metadata record with a plausible interface,
rate or sensor identity would incorrectly imply availability.

Audit-only fields such as TASK-001 `confidence` and `ambiguity` remain in
`vipro_inventory.yaml`, which is the evidence ledger. Manifest notes and signal
descriptions preserve interpretation needed to prevent misuse. Duplicating the
entire audit ledger inside every experimental manifest is not required for
representing experimental data and is therefore not a schema mismatch.

## B. Fields remaining `UNKNOWN`

The current manifest deliberately leaves the following unresolved:

- motor models and serial numbers;
- physical motor-to-drive, terminal and cabinet mapping;
- drive models, firmware, protocol and actual control modes;
- physical encoder type, resolution, sign, zero and timestamp source;
- gear ratios and coupling stiffness, backlash, geometry and part numbers;
- physical command, acquisition and feedback interfaces;
- motor current and its scaling/calibration;
- drive-internal torque estimate and its physical interpretation;
- independent shaft/port torque sensor and calibration;
- temperature and drive fault/status acquisition;
- physical sample rates, command rates, latency and jitter;
- clock synchronization and physical device timestamps;
- certified torque/current/speed/position/power/thermal limits;
- physical E-stop chain and approved operating envelope;
- mechanism and excitation identifiers for a real trial;
- configuration hash and concrete immutable data artifacts.

For all unavailable hardware values included in the manifest, the enforced
representation is:

```yaml
value: null
provenance: UNKNOWN
```

Zero, SIM defaults and placeholder Modbus values are not substituted for these
unknowns.

## C. Schema mismatch assessment

No blocking schema mismatch was found.

Important boundary decisions are:

1. `HardwareComponent` stores logical A/B/coupling identities even when model
   and serial fields are unknown. A logical identifier is not a claim that its
   physical terminal mapping has been verified.
2. Unavailable signals are not inserted into the current signal catalogue.
   Their absence, plus the explicit TASK-001 audit, represents the current
   state more accurately than hypothetical metadata would.
3. `DataTier` is assigned only to present SIM signals. No current CSV is
   declared a raw physical artifact; formal classification of runtime files
   remains TASK-003.
4. `TimePoint.monotonic_ns=0` is used only as the defined origin of the planned
   PairSim session/trial. It is not an observed OS monotonic or device time.
5. The numerical integration step is represented as SIM clock resolution. It
   is not reinterpreted as a measured 2 kHz hardware loop.

The schema does not presently carry an explicit signal availability state such
as `PLANNED`, `AVAILABLE`, or `ABSENT`. This is not required for the current
manifest because it catalogues available session signals. If TASK-006 later
needs a requirements catalogue containing unavailable future inputs and
outputs, that catalogue should remain a separate interface-contract artifact
or motivate a versioned schema extension. It is not justification for changing
TASK-002 during TASK-002R.

## D. Proposed schema changes

None for schema version `1.0.0`.

The existing Python model, JSON Schema, and tests remain unchanged. Any future
proposal to add signal availability, control/validation eligibility, or device
timestamp semantics must be based on TASK-006 and actual hardware evidence,
then introduced as a separately reviewed, versioned change.

## E. Physical ABB backend status

The current repository has **no physical ABB acquisition or control backend**.

`joint_emulator` accepts only `SimBackend`. `modbus_backend.py` is an
intentionally nonfunctional skeleton with unknown registers and scaling and is
not instantiated by the runtime. Consequently, the current manifest must not
be changed from `SIMULATION` to `HARDWARE` or `HYBRID`.

No physical encoder, current, drive-estimated torque, independent shaft torque,
temperature, drive status or physical application timestamp enters the ROS 2
graph.

## F. Interpretation of `tau_b` and `effort`

Current `tau_b` / `tau_b_cmd_nm` is the requested, model-derived and gated SIM
B command. `sensor_msgs/JointState.effort` is a direct visualization copy of
that value.

Therefore:

> Current `tau_b` and `JointState.effort` are not physical torque measurements
> and are not valid measurements of physical rendering fidelity.

They may be used to verify software plumbing or as the requested-torque side of
a future comparison. They cannot supply the independent quantity
`tau_physical` in:

```text
fidelity_error = tau_physical - tau_requested
```

Using either value as both controller output and validation reference would be
circular validation.

## Readiness and remaining ViPRO-00B blockers

### Schema readiness

The schema is ready to receive future physical ViPRO session metadata, provided
that actual hardware evidence populates the presently unknown fields. This is
data-contract readiness, not hardware or metrology readiness.

### ViPRO-00B blockers

1. No independent physical port-torque route is known.
2. No motor-current or drive-torque feedback is acquired.
3. No torque constant, gear ratio, efficiency/loss model or calibration is
   available for an indirect port-torque estimate.
4. No physical encoder acquisition or calibration is implemented.
5. No device/acquisition/application timestamps support requested-versus-
   realized temporal alignment.
6. No documented hardware limits or risk-approved operating envelope exists.
7. The physical drive protocol, mode, mapping, scaling and status semantics are
   unknown.
8. The current SIM model produces both the command and every available
   observation, so it cannot independently validate physical fidelity.

Until these blockers are resolved, ViPRO-00B cannot establish
`tau_physical - tau_requested`, and physical fidelity experiments must remain
blocked.
