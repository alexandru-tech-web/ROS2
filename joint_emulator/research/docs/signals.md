# ViPRO signal inventory — TASK-001

## Interpretation rule

The current signal set is generated by simulation. Names containing `tau`,
`encoder`, or `effort` do not turn a command/model variable into a physical
measurement. Every table below distinguishes source, transformation and
independence.

Rates are configured/nominal values, not measured rates. `UNKNOWN` is retained
where the code does not provide evidence.

### Rate distinction

The full launch configures `/joint/state` at 100 Hz
(`launch/full_sim.launch.py:112-115`). `encoder_monitor` processes and logs each
received state inside `on_state`, but publishes its latest kinematics on a
separate 50 Hz timer (`encoder_monitor_node.py:109-164`). Consequently there is
no single unqualified “encoder rate” in the implementation:

- source state rate: configured 100 Hz in full launch;
- synthetic encoder processing/log row attempt: per state callback;
- kinematics ROS publication: configured 50 Hz;
- physical encoder acquisition rate: `UNKNOWN`.

## Logging fields and timestamp sources

### State CSV

The exact schema is declared in `session_export.py:18-30`. Rows are written by
`SessionStateLogger` (`session_export.py:66-100`) from the latest SIM state.

- `time_s`: simulation time from `PairSim`;
- `time_utc`: `datetime.now(timezone.utc)` at log write;
- no sequence number;
- no OS monotonic timestamp;
- no device acquisition timestamp;
- no command-application timestamp distinct from state timestamp.

### Encoder CSVs

`encoder_core.py:188-230` defines:

- common-axis: `t_s,time_utc,pair,th_raw,th,om,acc`;
- six-channel: `t_s,time_utc,pair,side,motor_id,counts,th_raw,th,om,acc,om_raw,source`.

`t_s` is inherited SIM time. `time_utc` is created in the monitor callback
(`encoder_monitor_node.py:116-153`). It is not a motor/drive timestamp.

### Events

`session_export.py:27-30,103-112` stores SIM `time_s` and write-time UTC for
commands/configuration changes. It does not record command reception and
physical application as separate instants.

## Signals needed to determine the physical load experienced by A

| Required observable | Repository status | Minimum missing metadata |

| `q_B` | synthetic SIM only | same; independent channel mapping |
| `tau_B_requested` | SIM command exists | future drive command interface and application timestamp |
| `motor_current_B` | UNKNOWN/absent | register/channel, A scaling, phase/DC interpretation, timestamp, calibration |
| `drive_torque_B` | UNKNOWN/absent | algorithm/parameter dependence, unit/scaling, bandwidth, latency, uncertainty |
| `tau_port_sensor` | UNKNOWN/absent | sensor model/location, sign, range, conditioner, calibration, timestamp |
| `temperature_B` | UNKNOWN/absent | sensor location, unit, rate and time alignment |
| `fault/saturation state` | UNKNOWN/absent | drive status words and exact semantics |

Without a calibrated physical route, only the following can be computed:

```text
requested virtual load = tau_B command
```

The following remains unavailable:

```text
realized physical load on A = UNKNOWN
fidelity error = realized physical load - requested virtual load = UNKNOWN
```

## Signal-chain conclusions

1. The only confirmed torque values are commands/model outputs.
2. The six encoder channels are structurally useful for future A/B acquisition,
   but currently originate from three latent SIM coordinates.
3. No current, drive torque, external torque or temperature path exists.
4. Timing metadata is insufficient for physical end-to-end alignment.
5. ViPRO-00B requires physical documentation and at least one calibrated torque
   reference before any claim of load fidelity.
